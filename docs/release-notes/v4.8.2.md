## 中文

### 這個錯誤不是我印的,但是我造成的

那句話來自 **PyInstaller 的 onefile 啟動器**,不是 LagScope 的程式碼。原始碼在
`bootloader/src/pyi_security.c`:

```c
/* Ensure that same executable is used */
if (wcscmp(parent_executable_w, current_executable_w) != 0) {
    PYI_ERROR_W(L"Security validation failure: parent process has different executable!\n");
    return -1;
}
```

**為什麼會撞到它,要從 PyInstaller 的打包方式講起。** onefile 打出來的程式跑起來是**兩個
同名的行程**:

```
LagScope.exe  (啟動器) ── 解壓到 _MEIxxxx，然後生出 ──> LagScope.exe (真正的程式)
                                                          帶著 _PYI_PARENT_PROCESS_LEVEL
```

那個子行程一啟動就會檢查:「我的父行程是不是同一個執行檔?」不是就拒絕啟動——
這是 PyInstaller 防止有人偽造環境變數劫持它的機制。

**然後我做了什麼**:v4.8.1 我加了 `CloseApplications=force`,並且保留了 v4.6 就設好的
`RestartApplications=yes`。於是:

1. Restart Manager 現在**真的關得掉**程式了(這是 v4.8.1 修對的部分)
2. 它把**兩個** LagScope.exe 都關掉了
3. 然後 `RestartApplications=yes` 讓它把**兩個都重新啟動**
4. 被重啟的那個「子行程」環境裡還帶著 `_PYI_PARENT_PROCESS_LEVEL`,所以它以為自己是子行程,
   去檢查父行程——結果父行程是 Restart Manager,不是 LagScope.exe
5. **檢查失敗,跳出那個框**

`RestartApplications=yes` 從 v4.6 就在那裡了,只是**因為 Restart Manager 一直關不掉這個程式,
所以從來沒真的重啟過任何東西**,這個 bug 就一直沒被觸發。我把關閉修好的那一刻,就把它放出來了。

### 修法

`RestartApplications=no`,並且程式內建的「直接更新」改成傳 `/NORESTARTAPPLICATIONS`
而不是 `/RESTARTAPPLICATIONS`。**兩邊都要改**——只改一邊,另一邊還是會讓 Restart Manager
去重啟那個子行程。

程式要怎麼回來?安裝程式最後那個 **「立即執行 LagScope」** 的勾選項。那條路啟動的是一個
乾淨的入口行程(環境裡沒有 `_PYI_PARENT_PROCESS_LEVEL`),它會自己正確地生出子行程。

新增兩個測試,其中一個直接去讀 `installer.iss` 確認那行是 `no`——因為這個設定
和命令列旗標必須一致,而它們住在兩個不同的檔案裡,很容易改了一邊忘了另一邊。
把設定改回 `yes` 那個測試就會紅。

### v4.8.1 有沒有裝成功?

**很可能有。** 那個錯誤是「被重啟的殘留行程」發出來的,不是安裝失敗。
從開始選單開 LagScope 看看——能開就是裝好了,那個框只是善後沒做乾淨。

## English

### The error is not from this app, but it is my fault

The message comes from PyInstaller's onefile bootloader (`bootloader/src/pyi_security.c`),
which is the definitive source I checked rather than guessing.

A onefile build runs as **two processes with the same name**: a launcher, and the application
it spawns. The child carries `_PYI_PARENT_PROCESS_LEVEL` in its environment and, on startup,
verifies that its parent runs the same executable - a defence against someone hijacking it
with a forged environment.

v4.8.1 added `CloseApplications=force` while leaving `RestartApplications=yes` from v4.6. So
Restart Manager could finally close the app (which was the fix), closed **both** processes,
and then restarted both. The restarted *child* still believed it was a child, checked its
parent, found Restart Manager, and refused to start.

`RestartApplications=yes` had been there since v4.6. It never did any harm because Restart
Manager could never close this app in the first place - fixing the close is what let the
latent bug out.

### The fix

`RestartApplications=no`, and the in-app updater passes `/NORESTARTAPPLICATIONS` instead of
`/RESTARTAPPLICATIONS`. Both were needed: either one alone still lets Restart Manager relaunch
the child. The installer's own "run now" step brings the app back as a clean entry-point
process, which spawns its child correctly.

Two new tests, one of which reads `installer.iss` directly to assert the directive - the
script and the command-line flag have to agree and they live in different files.

### Did v4.8.1 install?

Probably yes. The error came from a restarted leftover process, not from a failed install -
start LagScope from the Start menu and see.
