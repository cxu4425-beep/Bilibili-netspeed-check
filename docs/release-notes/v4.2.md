## 中文

### 這些 bug 是怎麼被找到的

專案從第一個 commit 起就有 CI，會在 Windows / macOS / Ubuntu 上跑全部測試。
**它從第 1 次到第 24 次執行沒有一次是綠的，而中間發了 8 個版本，沒有人去看。**

去把那片紅燈讀完，裡面躺著四個真的 bug。現在五個平台組合全綠。

### 🪟 Windows：手機儀表板的埠會被搶

`HTTPServer` 會設 SO_REUSEADDR。這個選項在 Unix 上只是「允許重用還卡在 TIME_WAIT 的埠」，
在 **Windows 上卻是「就算現在有別人佔著也搶過來」**。

後果：兩份 LagScope 同時開，或是別的程式已經佔著 23125，**兩邊都會 bind 成功**，
請求進到哪一個 socket 由核心決定。程式碼裡 `start()` 一直宣稱「埠被佔用就回報失敗」，
在 Windows 上其實從來沒做到。

現在在 Windows 上關掉這個旗標，行為和它宣稱的一致了。

### 🗂 客戶端資料夾被重複掃描

候選資料夾名單故意有好幾種拼法（`bilibili`、`BiliBili`…），因為不同版本的客戶端不一樣。
但在**不分大小寫的檔案系統**上——Windows，以及預設設定的 macOS——這些是**同一個資料夾**。
去重是用路徑文字比對的，所以兩個拼法都留下來，於是每次掃描都把同一個 History 資料庫讀兩遍。

改成用 device + inode 當識別：不管是換大小寫、symlink 還是 junction，同一個資料夾就是同一個。

### ⏰ 開機第一分鐘沒有時鐘校正（影響開機自動啟動）

這個最值得講。

`time.monotonic()` 在 Linux 上是**開機到現在的秒數**，而「還沒同步過時鐘」存的是 `0.0`。
所以那個判斷實際上讀作「**開機未滿 60 秒就跳過**」，第一次時鐘同步被整個略過。

會踩到的是誰？**勾了「開機自動啟動」的人**——開機、程式自動起來、
第一分鐘的「實測」延遲完全沒有時鐘偏移校正。過了 60 秒它自己會好，
所以從來不像個 bug，只是那一分鐘的數字不準。

同一類錯誤在 1.2 版的自動偵測那邊修過一次，這個位置當時漏掉了。

### 🕐 bridge 的「timeout = 0」不等於「都不信」

過期判斷用的是嚴格大於。Windows 的時鐘精度約 15 ms，所以剛送達的回報年齡可能正好是 `0.0`，
`0.0 > 0.0` 不成立，於是被當成新鮮的。改成 `>=`——在預設的 120 秒完全無感，
在 0 的時候才符合字面意思。

### 每個修正都有測試守著

四個修正各自配一個**拿掉修正就會失敗**的測試，而且都能在任何平台上驗證：

- 用 symlink 模擬不分大小寫的檔案系統（Windows/macOS 上本來就有，不用做）
- 埠的判斷寫成吃平台字串的函式，不是讀當前機器
- 用假的 `monotonic()` 模擬剛開機的機器

395 個測試，Windows / macOS / Ubuntu 3.9 / 3.11 / 3.12 全綠。

## English

### How these were found

The project has had CI running the full suite on Windows, macOS and Ubuntu since its first
commit. **It had never once been green - 24 runs, 24 failures, across eight releases, and
nobody looked.** Reading that red properly turned up four real bugs. All five platform
combinations pass now.

### Windows: the phone dashboard could have its port stolen

`HTTPServer` sets SO_REUSEADDR. On Unix that only permits rebinding a port stuck in
TIME_WAIT; on **Windows it means "take this port even if something is bound to it right
now"**. Two copies of LagScope, or LagScope and anything else already on 23125, would both
bind successfully and requests would land on whichever socket the kernel picked. `start()`
had always claimed to report a taken port; on Windows it never did. The flag is now off
where it means that.

### The client's data folder was scanned twice

The candidate names are spelled several ways on purpose (`bilibili`, `BiliBili`, …) because
builds differ - but on a case-insensitive filesystem, which means Windows and a default
macOS volume, those are one directory. Deduplicating by path text kept both, so every scan
read the same History database over again. Identity is now the device and inode pair, which
is the same whichever name, symlink or junction it was reached through.

### No clock correction for the first minute after boot

`time.monotonic()` is uptime on Linux, and "never synced yet" was stored as `0.0`, so the
guard read "if uptime is under 60 seconds, skip" - and skipped the first clock sync
entirely. The people who hit this are the ones who enabled **start with the system**: the
first minute of "measured" latency ran with no clock offset at all. It healed itself once
uptime passed the interval, which is exactly why it never looked like a bug. The same
sentinel-versus-uptime mistake was found and fixed in the detection scanner back in 1.2;
this instance was missed then.

### A bridge timeout of zero did not mean "trust nothing"

The staleness check was strictly greater-than, and Windows' clock granularity is about
15 ms, so a report that had just arrived could be exactly 0.0 old and count as fresh. Now
`>=`, which changes nothing at the default 120 seconds and makes zero mean what it reads
like.

### Each fix is pinned

Every one has a test that fails without it, and each is verifiable from any machine: a
symlink stands in for a case-insensitive filesystem, the port decision is a function of a
platform name rather than of the host, and a fake `monotonic()` stands in for a machine
that just booted.

395 tests, green on Windows, macOS and Ubuntu across Python 3.9, 3.11 and 3.12.
