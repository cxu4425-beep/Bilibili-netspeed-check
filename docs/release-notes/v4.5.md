## 中文

### 🌏 你被分到哪台 CDN——直接寫在報告上

B 站的邊緣節點主機名不是亂碼,它本身就寫了答案:

```
cn-hbyc-ct-01.bilivideo.com
│  │    │  └── 節點編號
│  │    └───── ct = 中國電信
│  └────────── hbyc = 湖北宜昌
└───────────── cn = 中國大陸
```

現在報告和 `--selftest` 會直接翻出來:`cn-hbyc-ct-01` → **宜昌 · 中國電信**;
`upos-sz-mirrorhw` → **華為雲 CDN**;`cn-gotcha09` → **B 站自建節點 · 中國大陸**。

這件事之所以重要:**「為什麼會卡」多半是「你被分到哪台機器」的問題,不是「你頻寬夠不夠」的問題。**
以前你只看得到一串主機名,等於看不到答案。

**它有一條刻意的規矩:認不出來的就說認不出來。** 省市代碼是唯一能靠猜的部分,所以只查
一張「有把握的」對照表,查不到就把原始代碼原封不動印出來:

```
cn-hbyc-ct-01  ->  宜昌 · 中國電信          ← 查得到
cn-hbqq-cu-02  ->  湖北 (hbqq) · 中國聯通    ← 省份讀得出,城市不硬猜
cn-zzz-ct-01   ->  中國大陸 (zzz) · 中國電信  ← 只認得出國別
```

編一個看起來很像的城市名比說「不知道」糟得多,因為會有人照著它去做決定。

**還有一項會特別警告:PCDN／P2P 節點。** 主機名長得像 `xy118x123x45x67xy.mcdn.bilivideo.cn`
的那種——它把 IP 直接編進主機名裡——**那不是機房機器,是別人家的寬頻在賣閒置上行**。
線路測起來明明正常卻一直卡,被分到這種節點是很常見又完全看不見的原因。現在它會直接說出來。

### ⏱ 修正:延遲數字裡本來混了 DNS 解析時間

這是本程式自己的量測錯誤,不是顯示問題:

```python
sock = socket.create_connection((host, int(port)), timeout=timeout_s)
```

`create_connection` 收的是**主機名**,所以它會先做 DNS 解析——**那段時間一直被算進「伺服器延遲」裡。**
B 站 CDN 的 DNS TTL 很短,會頻繁重新解析,這個誤差不是固定偏移,是會跳動的。

現在改成:先解析、記下時間,再對**解析出來的位址**計時握手,兩個數字分開報。
`tcp_rtt_ms()` 的簽名沒動,所有既有呼叫端不受影響。

### 🔍 `--why-ping`:直接告訴你為什麼跟 CMD 量的不一樣

```
lagscope --why-ping                          # 目前在量的那台
lagscope --why-ping cn-gotcha09.bilivideo.com
```

```
主機名: cn-hbyc-ct-01.bilivideo.com
實際連到: 203.0.113.45:443
這台是: 宜昌 · 中國電信

  TCP 握手（本程式用的）             最快   62.4 ms   中位數   64.1 ms
  ICMP ping（CMD 用的）              最快   21.0 ms   中位數   21.3 ms
  DNS 解析                                 18.7 ms   （已經不算進上面的數字裡）

差距（TCP 減 ICMP）: +41.4 ms
差很多。這台機器對 ICMP 和 TCP 的處理明顯不同——路由器和 CDN 常把 ICMP 丟到低優先級、
限速,或乾脆由前面的設備代答。這種情況下 ping 的數字不能拿來判斷你看直播會不會卡,
TCP 的才算數。

拿這個跟 CMD 的 ping 比之前,先確認你 ping 的是上面那個「實際連到」的位址。
```

**兩邊是對同一個解析後的位址各量五次**,所以比對本身是公平的。然後它會說出四個常見原因裡
哪一個成立——包括最常見、也最容易被忽略的那個:**你 ping 的根本不是同一台機器**
(ping `www.bilibili.com`,但推流給你的是某台 CDN 邊緣節點,可能差好幾個省)。

## English

### Which CDN you were assigned, written down

Bilibili's edge hostnames state who runs the node, often where it is, and which carrier it
sits behind. `cn-hbyc-ct-01` is Yichang on China Telecom; `upos-sz-mirrorhw` is Huawei Cloud;
`cn-gotcha09` is Bilibili's own edge. The report and `--selftest` now say so.

That matters because "why does it stutter" is usually a question about *which machine you were
assigned*, not about how much bandwidth you have - and a hostname a viewer cannot read is an
answer they cannot act on.

The location is the guessable half, so it is looked up in a table of codes we are confident
about and otherwise handed back raw: `cn-hbqq-cu-02` reports Hubei and the unrecognised code,
never an invented city. A plausible wrong city is worse than an admitted unknown, because
somebody would act on it.

Peer-assisted (PCDN/mCDN) nodes get a warning of their own. A hostname like
`xy118x123x45x67xy.mcdn.bilivideo.cn` spells an address out inside itself; those are consumer
connections reselling spare upstream rather than datacentre machines, and being handed one is
a common and entirely invisible reason for a stream that stalls on a line that tests fine.

### Fixed: the latency figure included the DNS lookup

`tcp_rtt_ms` timed `create_connection(hostname)`, which resolves - so the name lookup was
quietly billed to the server's latency on every sample. That is a measurement error rather
than a presentation one, and with the short TTLs on CDN names it was a moving one, not a
constant offset. Resolution and handshake are now timed separately and reported separately.
`tcp_rtt_ms()` keeps its signature, so every existing caller is unaffected.

### `--why-ping`

Times ICMP and a TCP handshake against the *same resolved address*, five rounds each, prints
them side by side with the lookup on its own line, and then says which of the four ordinary
explanations the numbers support - rather than leaving the reader to guess, or insisting the
tool is right.

The most common explanation is the one people miss: `ping bilibili.com` reaches the front
door, while this measures the edge actually serving the stream, and they can be in different
provinces.
