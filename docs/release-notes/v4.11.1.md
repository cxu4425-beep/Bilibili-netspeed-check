## 中文

### 🔎 真機報告找出來的三件事

**① `6 endpoint(s), 0 distinct edge(s)`——旁邊明明列著六個不同的主機名稱**

`fetch_endpoints()` 會回傳清單但**不寫入快取**，而 `hosts_available()` 讀的正是那個快取；
只有監測路徑會去填它。數字不對只是表面。

**真正的代價是**：每個節點的解碼迴圈跑在同一個空清單上，所以 **PCDN 偵測從來沒有作用過**——
不管伺服器給你幾個 PCDN 節點，那個警告都不可能出現。那項檢查一直在空轉。

這也解釋了為什麼後面「CDN 節點」那項**有**列出六個：`check_measure` 夾在兩者中間，
它會經過填快取的那條路。

> **實際量測不受影響。** 監視器走的是 `_endpoints_for`，那條路徑會填快取。只有自我檢測踩到。

**② fmp4 不等於能精確量測**

方法論文件寫著 B 站的 fmp4 播放清單「通常帶有」`EXT-X-PROGRAM-DATE-TIME`。
真機拿到的海外節點給了 fmp4，**卻沒有 PDT**，於是退回估算法。

而自我檢測的警告寫成「不是 fmp4 → 會變估算」，等於暗示拿到 fmp4 就能實測。
**fmp4 是唯一「可能」精確量測的格式，不是「一定」會精確量測的格式。**
文件和程式的措辭都改了，並把這次的觀測記進文件當證據。

**③ 報告裡有你的 Windows 帳號名稱，而它自己說沒有**

```
config folder: C:\Users\<你的帳號>\AppData\Roaming\LagScope
...
裡面只有你家內網位址和被測伺服器，沒有 Wi-Fi 名稱、公網 IP 或帳號。
```

這份輸出**就是設計來貼到論壇或寄給客服的**，所以那句話必須是真的。
現在會遮成 `%USERPROFILE%\AppData\Roaming\LagScope`，
連 `Path.home()` 對不上的重導向設定檔也會遮。

### 🎧 藍牙耳機延遲校正（電腦 + Android）

程式量的東西全部止於**畫面**。用藍牙聽的人在那之後還有一段，通常 100–250 毫秒，
比顯示延遲大得多——而**沒有任何作業系統會把這個數字交出來**：

- Windows 沒有公開 API 可以問到目前 A2DP 用哪個編解碼器
- Android 的 `BluetoothCodecConfig` 需要只有系統程式拿得到的權限
- 系統回報的音訊延遲不含無線鏈路和耳機自己的 DSP，會嚴重少報

所以用量的。放一聲、畫面在你設定的毫秒數之後閃一下，你調到兩者重合為止——
那個數字就是「聲音比畫面晚多少」，直接補進總延遲。

沒有用 QtMultimedia（`PySide6-Essentials` 不含它，為了放一聲換完整版不划算）：
用標準函式庫在記憶體裡生一個 WAV，Windows 交給 `winsound`。

**誠實的界線**：精度就是人耳的精度（20–40 毫秒）；量到的是**差值**，包含電腦自己的音訊管線，
不是耳機內部的絕對延遲。非 Windows 上每次響聲要另起行程，那段時間會被算進去，數字偏大——
程式會把這件事顯示在校正畫面上。

### 📶 看是哪個 Wi-Fi 在拖你

Wi-Fi 的讀取本來就有，但只在按「網路體檢」時跑一次、看完就丟。現在**每分鐘記下來**，
然後套用跟 CDN 節點**完全同一套比較**：

```
by_edge  → 你被分到哪個節點   ← 你決定不了
by_link  → 你在哪個無線網路   ← 你決定得了
```

於是它說得出「**你在 2.4 GHz 的時候慢了 750 ms，而你有一半的時間在上面**」。

- **頻段是推導的，推不出就不說**。Wi-Fi 6E 的頻道編號從 1 重新開始，落單的「5」可能是
  2.4 也可能是 6 GHz。猜錯的代價是**叫人去改一個本來就對的設定**。
- **分組的鍵是 SSID + 頻段**，因為很多路由器兩個頻段同名，只看名字會剛好把最該分開的兩個平均在一起。
- **BSSID 換手偵測**：有 mesh 或延伸器時換 AP 的過程中 SSID 完全不變，斷那一到三秒
  以前看不出原因。現在說得出來。
- **2.4 GHz + 藍牙**會提醒它們共用同一段無線電——但這條**標明是推論不是量測**，
  程式並沒有觀測到干擾。

### 📍 伺服器在哪

解碼 4.5 就做了，但答案只出現在歷史表格和報告裡，沒有地方可以「現在看一眼」。
而且它對**租用公有雲的節點和 PCDN 完全沒轍**——`upos-sz-mirrorhw` 只說得出「華為雲」。

所以加了第二個來源：**光速**。

```
299,792 km/s ÷ 1.468（光纖）÷ 2（往返走兩趟） ≈ 每毫秒 102 公里
```

| 往返 | 至多多遠 | |
| --- | --- | --- |
| 4 ms | 408 km | ✅ 很有力——它就在附近，沒得爭 |
| 38 ms | 3,880 km | ✅ 還算有用 |
| 260 ms | 26,000 km | ❌ 地球半圈，等於沒說 |

**這是上限不是估計值**，而且對每一台伺服器都有效——名稱說不說話都一樣。
上限超過 10,000 km 就不顯示，因為那描述的是整顆星球。
往返時間不是量到那個節點時（監視器會退回量 API 主機）也不顯示。

**不用 GeoIP**：內建資料庫出貨當天就開始過期，而且對 CDN 位址惡名昭彰地不準
（常常回報註冊者總部而不是機房）；線上查詢等於把你看過的每個東西的位址送給第三方。
上面那套只要一個乘法。

## English

**The headline is a bug report, not a feature.** The first self-test run against a
live room exposed three faults:

1. **`0 distinct edge(s)` beside six distinct hostnames.** `check_endpoints` calls
   `fetch_endpoints()`, which returns without storing; `hosts_available()` reads a
   cache only the monitoring path fills. The count was cosmetic — but the per-host
   loop ran over the same empty list, so **the PCDN warning could never fire**,
   however many peer nodes were offered. Monitoring was never affected.
2. **fmp4 does not guarantee an exact measurement.** A real overseas edge served
   fmp4 with no `EXT-X-PROGRAM-DATE-TIME`, falling back to the window estimate.
   The doc said "usually" and the self-test's warning implied fmp4 meant measured.
   Both now say what is actually true.
3. **The report printed `C:\Users\<name>\...` two lines above its own promise to
   carry no account details.** That output exists to be pasted into a forum thread,
   so the promise has to be true. Home paths are now redacted.

**Also in this release, since 4.8.3:**

- **Bluetooth headset calibration**, desktop and Android. No OS reports this number
  — Windows has no public API for the A2DP codec, Android's `BluetoothCodecConfig`
  needs a system permission — so it is measured by ear: a click plays, the panel
  flashes an adjustable amount later, you align the two. Precision is human
  (20–40 ms) and the result is a *difference*, not the headset's absolute latency.
- **Which wireless link is slowing you down.** The radio state is now recorded per
  minute and compared with the same machinery that compares CDN edges — so it can
  say "you are 750 ms slower on the 2.4 GHz network, and you are on it half the
  time". Band is derived and left blank when Wi-Fi 6E makes the channel ambiguous;
  BSSID changes are counted, because a mesh roam is a stall with no other visible
  cause.
- **Where the server is**, live. The hostname decoder covers named edges; physics
  covers the rest — a signal cannot have travelled further than light allows in the
  round-trip time (~102 km per ms). A ceiling, never an estimate, hidden when it is
  too wide to mean anything. Deliberately not GeoIP.

**Verified vs not:** the distance arithmetic and the timing loops are fully tested
here; the Wi-Fi parsing is tested against captured tool output but never against a
real adapter; **the Windows sound path for the Bluetooth calibration has never
executed anywhere**, and the Android APK has never run on a phone. 660 tests green
across three platforms and three Python versions.

> The APK is built and unit-tested in CI but is **not attached to this release**:
> that needs the `ANDROID_KEYSTORE_BASE64` and `ANDROID_KEYSTORE_PASSWORD` secrets.
