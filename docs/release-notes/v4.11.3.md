## 中文

### 🔇 那一行是 CPython 明文禁止的

程式碼是:

```python
winsound.PlaySound(wav_bytes, winsound.SND_MEMORY | winsound.SND_ASYNC)
```

CPython 的 `PC/winsound.c` 直接拒絕這個組合:

```c
} else if (flags & SND_MEMORY) {
    if (flags & SND_ASYNC) {
        PyErr_SetString(PyExc_RuntimeError,
                        "Cannot play asynchronously from memory");
```

非同步呼叫會在**還握著一塊不屬於自己的緩衝區**時就返回,所以這個模組乾脆不讓你用。

而我在那一行上面的註解寫的是:「SND_ASYNC 會先返回,所以緩衝區要活得比呼叫久」——
**我推理出了那個危險,然後寫下了因為那個危險而被禁止的組合。**

`play()` 的 `except Exception` 把 RuntimeError 吞掉、回傳 False,
對話框於是把自己的按鈕變灰:沒聲音、不閃、也沒有任何說明。

### 修法

改成寫進暫存檔,用 `SND_FILENAME | SND_ASYNC | SND_NODEFAULT`——
**檔名是可以非同步播放的**,而那個暫存檔本來就為了 Linux/macOS 那條路徑存在。

不改成同步播放的原因:那會讓 UI 執行緒卡在音訊裝置上,
而藍牙耳機的音訊裝置**正是這個功能要量的東西**。

### 🗣 而且現在它會說話

以前失敗只是默默把按鈕變灰,使用者就對著一個什麼都不做的對話框發呆——那正是這次的回報內容。
現在會顯示發生了什麼事,並附上系統回的訊息。

兩種訊息分開,因為那是兩種不同的故障:
**開始之前就找不到播放程式**,和**開始之後播放被拒絕**,不是同一回事。
跟 Windows 使用者說「這台機器找不到可以放音的程式」會讓他往完全錯的方向找。

### 怎麼守住

六個新測試把 Windows 那條路徑跑過一遍,用一個**行為跟真的 winsound 一樣**的替身——
它會用同一條規則拒絕同一個組合。把舊的呼叫放回去,其中五個會變紅。

這是這台機器上唯一能驗證那條路徑的辦法:winsound 是 Windows 專屬的 C 擴充,
而這裡沒有 Windows,也沒有音效裝置。

## English

**The call CPython refuses.** The click was played with
`SND_MEMORY | SND_ASYNC`, and `PC/winsound.c` rejects that pair outright with
*"Cannot play asynchronously from memory"* - an async call would return while still
holding a buffer it does not own. The comment directly above the line reasoned about
that very hazard and then wrote the combination the hazard forbids. `play()` caught
the RuntimeError, returned False, and the dialog greyed out its own Start button: no
sound, no flash, no explanation.

**The fix.** The click goes to a temporary file and Windows plays it with
`SND_FILENAME | SND_ASYNC | SND_NODEFAULT` - async works from a filename, and the
file already existed for the POSIX path. Playing synchronously instead would block
the UI thread on the audio device, which on a Bluetooth headset is the very thing
being measured.

**And it now says what happened,** instead of leaving a dialog that does nothing.
Two messages, because no audio program found before starting is not the same fault
as playback refusing once it did.

**Guarded by six tests** that drive the Windows path through a stand-in `winsound`
enforcing the same rule the real one does. Restoring the old call fails five of them.
That is the only way this path can be checked here: `winsound` is a Windows-only C
extension, and this machine has neither Windows nor an audio device.

670 tests green across three platforms and three Python versions.
