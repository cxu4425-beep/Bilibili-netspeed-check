> 兩個新功能：**「我改的設定有用嗎」前後對照**，和 **`--selftest` 自我檢測**。
> **沒有破壞性變更**，舊設定和已經記下的歷史都照常沿用。
>
> Two additions: a **before-and-after comparison** for changes you make, and a
> **`--selftest`** that runs every probe against the real world. Nothing breaks.

## 中文

### 🔬 我改的設定有用嗎

這個工具一路做下來的邏輯是：量到延遲 → 說是誰的錯 → 說什麼時候壞 → CDN 自己換。
缺的是最後一步——**報告說你 Wi-Fi 訊號弱，你去換了 5GHz，然後呢？**

以前只能憑感覺。現在按托盤選單的 **標記此刻（我改了設定）…**，輸入你改了什麼，
之後報告就會多一段：

![標記前後的走勢](https://raw.githubusercontent.com/cxu4425-beep/LagScope/v4.3/docs/images/history-marked.png)

```
我改的設定有用嗎
  08-29 12:30   換到 5GHz
      218 ms → 87 ms    好轉了，快了 131 ms    (前後各 1.5 小時)
```

走勢圖上會畫一條虛線標出那一刻，**匯出的體檢報告裡的圖也有**，所以寄給客服的那份一看就懂。

**這個功能最重要的部分是它怎麼避免騙你。** 前後用的是**一樣長**的時間窗口，
取兩邊都有資料的**較短**那段：

| 規則 | 為什麼 |
| --- | --- |
| 前後窗口**等長**，取較短那邊 | 拿一整晚的「之前」比五分鐘的「之後」，什麼改動都會「有效」 |
| 最長各 **6 小時** | 「之前」不會跨到完全不同的另一個晚上 |
| 每邊至少 **5 分鐘**，否則不給結論 | 兩分鐘的資料只是雜訊 |
| 差距 **10 ms 以內**算「沒有明顯差別」 | 不把測量誤差說成改善 |
| 平均、P95、丟包率都比 | 只看平均會漏掉「偶爾爆一下」 |

資料不夠時它直接說「資料不夠，看不出來」，不硬給結論。變差了也會直說「反而差了 X ms」。

### 🩺 自我檢測 `--selftest`

**先講清楚一件事**：這個程式所有 B 站相關的程式碼——playurl 解析、HLS 伺服器時鐘、
FLV 關鍵影格、CDN 比較與自動切換——**都是對著測試資料寫出來的**，
因為開發環境連不上 B 站。單元測試能證明「給定這種格式，解析是對的」，
不能證明「B 站現在還是這種格式」。

```bash
lagscope --selftest              # 不含 B 站的部分
lagscope --selftest 21452505     # 帶一個正在直播的房間號，涵蓋全部
```

它把每個探測對真實世界跑一次，把拿到什麼**原封不動印出來**，不做任何斷言：

```
[ ok ] Bilibili API reachable
        TCP handshake: 18 ms
        API answered, code=0
[ ok ] play URLs
        6 endpoint(s), 3 distinct edge(s)
        chosen: fmp4 on cn-gotcha09.bilivideo.com
[ ok ] live measurement
        method: hls-pdt   measured
        stream: 2310 ms   host: cn-gotcha09.bilivideo.com
[ ok ] CDN edges
        cn-gotcha09.bilivideo.com     48 ms
        cn-hbyc-ct-01.bilivideo.com   210 ms
        it moved: cn-hbyc-ct-01... -> cn-gotcha09... (saving 162 ms)
[warn] path tools (ping / gateway)
        no usable ping command - the segment check cannot run here
```

有問題把整段貼進 issue 就夠了。順帶一提，寫這個功能的時候它立刻抓到自己的一個弱點：
原本只做 TCP 握手就報「連得上」，但在有 proxy 的機器上握手成功而 API 其實被擋。
現在會真的送一個請求出去問 API，握手成功但 API 不通會如實報 FAIL。

**輸出裡沒有什麼**：沒有 Wi-Fi 名稱、沒有公網 IP、沒有帳號、沒有其他程式的資訊。
出現的位址只有你家內網的和被測伺服器，房間號是你自己給的。

## English

### Did the change help?

The arc of this tool has been: measure the latency, name the culprit, say when it broke, move
the CDN edge by itself. The missing step was the last one - **the report says the Wi-Fi is
weak, you move to 5GHz, and then what?**

**Mark this moment…** records what you changed, and the report compares the periods either
side of it. A dashed line marks it on the chart, in the window and in the exported report.

The honesty of that comparison is the feature. Both sides use **the same length of time** -
the shorter of what is available either way, capped at six hours and refused below five
minutes. Six hours of "before" against five minutes of "after" makes almost any change look
like a triumph, and that is how this sort of feature usually lies. A difference under 10 ms
is reported as no real difference rather than dressed up, a regression is stated as one, and
average, p95 and packet loss are all compared, because the average alone hides "it spikes
occasionally". Where there is not enough data it says so instead of guessing.

### Self-test

Every Bilibili code path here was written against fixtures, because the machine it was
written on cannot reach Bilibili at all. The unit tests prove the parsing is right *given
that shape of input*. They cannot prove the input still has that shape.

`lagscope --selftest [room-id]` runs each probe once against the real thing and prints what
came back, asserting nothing - evidence for a person to read and paste into a bug report.

Writing it immediately caught a weakness in its own first draft: the reachability check did
only a TCP handshake, which succeeds against a proxy while every request to Bilibili is
refused. It now asks the API a real question and reports a failure when the answer does not
come, rather than a comfortable "ok".

The output carries addresses inside your own network and the servers measured. No Wi-Fi
name, no public IP, no account, nothing about anything else running on the machine.
