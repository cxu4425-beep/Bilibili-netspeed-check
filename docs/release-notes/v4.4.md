## 中文

### 🚀 測一下這條線到底多快

狀態列上的 `↓46.8M` 一直都在，但它是**被動**的——你的機器**現在正好**在搬多少資料。
它能回答「是不是有別的東西在吃頻寬」，但回答不了「這條線最快能跑多少」，
因為那個當下根本沒有人在要求它跑快。

托盤選單的 **測一下網速…** 會真的去要求：

```
下載速度：94.2 Mbps

足夠 4K（25 Mbps 以上）

測的是你正在看的那個 CDN——也就是真正影響你的那條路。
用掉 80 MB，花了 9 秒。
```

**這個功能有兩個副作用，而它們比那個數字本身更重要**，所以按下去之前會先問你一次：

| | |
| --- | --- |
| **它會把線佔滿** | 測的時候延遲一定會飆高、直播可能會卡。**這是它自己造成的**，所以它會**先**在歷史紀錄上標一筆「測速（延遲飆高是正常的）」，免得你等一下看走勢圖，把自己造成的那根尖峰當成故障在查。這個程式一路做下來就是為了找出「誰造成的」，那它自己造成的那一根當然要自己認。 |
| **它會用掉流量** | 預設**時間和流量各有上限**（10 秒 / 80 MB），先到哪個就停哪個。所以千兆的線是停在 80 MB，而不是為了「跑滿 10 秒」拉掉一個 GB。兩個上限都能在設定裡改。 |

**它去哪裡下載是刻意的**：優先用**你正在看的那個 CDN 節點**。
會不會卡取決於你到那台機器的那條路，而不是你到某個測速網站的那條路——那兩條常常根本不同家，
所以「測速網站跑到 300M，B 站還是卡」這種事才會一直發生。這個測速量的就是那條會卡的路。
真的沒有在看東西時，才退回公開測速點（Cloudflare）。

結果會寫進**體檢報告**裡，所以寄給客服的那份會同時有「延遲多少」和「線多快」。
沒有 GUI 的話：`lagscope --speedtest`。

**順帶處理掉的一個誤差**：TCP 連線剛建立的頭一秒鐘一定慢（慢啟動），
把那一秒平均進去會讓一條快線看起來很平庸。所以開頭那段是**單獨算完丟掉**的，只有暖機後的算數。
真的太快就結束（檔案太小或線太慢）連暖機都沒跑完時，它會直接說「這個數字可能偏低」，
而不是假裝那就是你的線速。

新增的 20 個測試不是對著真的測速站跑的——是對著一台**被限制在每秒 4 MB 的本機伺服器**跑的。
連到真的站台只能證明「網路是通的」；只有速率已知，才能驗證它算出來的 32 Mbps 是對的、
而且慢啟動真的有被丟掉。

## English

### How fast is this line, really?

The `↓46.8M` in the status row is *passive* - what the machine happens to be moving right
now. That answers "is something else eating my bandwidth" and cannot answer "how fast could
this line go", because nothing was asking it to go fast. **Speed test** in the tray menu asks.

Two things about it matter more than the number, which is why it confirms first.

**It saturates the line.** Latency spikes and the stream may stutter. Because that is
self-inflicted, the app marks those minutes in the history *before* starting, so the spike is
not later investigated as a fault. A tool whose whole purpose is attributing blame should
start by owning the damage it does itself.

**It costs data.** Time *and* bytes are both capped - 10 seconds or 80 MB, whichever comes
first - so a gigabit line stops at the byte cap rather than pulling down a gigabyte to fill
its ten seconds. Both limits are settings.

Where it downloads from is deliberate: the CDN edge already serving what you are watching.
Whether you stutter depends on the path to *that* machine, not the path to a speed test site,
and they are frequently not even the same carrier - which is exactly why "the speed test says
300 Mbps and the stream still stutters" is such a common and such a useless observation. This
measures the path that stutters. Only when nothing is being watched does it fall back to a
public endpoint (Cloudflare).

The result goes into the exported report, so the file you send to support carries both the
latency and the line speed. Headless: `lagscope --speedtest`.

The opening second of a connection is slow, and averaging TCP slow start in makes a fast line
look mediocre, so that stretch is measured separately and thrown away. A download that ends
before the warm-up finishes is reported as possibly reading low rather than presented as the
line speed.

The 20 new tests do not run against a real speed test endpoint. They run against a local
server **held to 4 MB/s**, because reaching a real one would only prove the network works;
only a known rate can prove the arithmetic produces 32 Mbps and that slow start was actually
discarded.
